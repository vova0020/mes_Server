# Исправление расчета machine-uptime

## Проблема

Эндпоинт `/api/statistics/machine-uptime?dateRangeType=DAY` выдавал неверные данные из-за **двух логических ошибок**:

### Ошибка 1: Неправильный начальный статус периода

В методе `calculateStatusBreakdown` начальный статус периода определялся неправильно:

```typescript
// НЕПРАВИЛЬНО ❌
const previousHistory = history.length > 0 ? history[0].newStatus : currentStatus;
```

Код брал **первую запись из истории ВНУТРИ периода** (`history[0].newStatus`), но это новый статус после изменения, а не тот статус, с которого начинался период!

### Ошибка 2: Неправильная обработка дат в CUSTOM режиме

При передаче дат в формате `2026-06-23`, конструктор `new Date('2026-06-23')` создает дату в UTC:

```typescript
// НЕПРАВИЛЬНО ❌
startDate = new Date(dto.startDate!); // → 2026-06-23 00:00 UTC = 2026-06-23 03:00 МСК
```

Результат: период начинался с **03:00** вместо **00:00** по московскому времени!

### Пример проблемы:

Допустим:
- 00:00 - станок был в статусе `ACTIVE`
- 10:00 - станок переключился в `INACTIVE`
- 15:00 - станок переключился в `MAINTENANCE`

При запросе за день (с 00:00 до текущего момента):
- **Старая логика** брала первое изменение (10:00, `INACTIVE`) как начальный статус
- **Результат**: период с 00:00 до 10:00 считался как `INACTIVE` ❌
- **Правильно**: период с 00:00 до 10:00 должен считаться как `ACTIVE` ✅

## Решение

### 1. Получаем статус ДО начала периода

В методе `getMachineUptimeStats` добавлен запрос для получения последнего статуса ПЕРЕД началом периода:

```typescript
const statusBeforePeriod = await this.prisma.machineStatusHistory.findFirst({
  where: {
    machineId: machine.machineId,
    createdAt: {
      lt: startDate, // МЕНЬШЕ чем начало периода
    },
  },
  orderBy: {
    createdAt: 'desc', // Берем самую последнюю запись
  },
  select: {
    newStatus: true,
  },
});

// Начальный статус - либо последний перед периодом, либо текущий
const initialStatus = statusBeforePeriod?.newStatus || machine.status;
```

### 2. Исправлен метод calculateStatusBreakdown

Теперь метод принимает корректный `initialStatus` как параметр:

```typescript
private calculateStatusBreakdown(
  history: Array<{ newStatus: MachineStatus; createdAt: Date }>,
  initialStatus: MachineStatus, // ← Теперь передается корректный начальный статус
  startDate: Date,
  endDate: Date,
): StatusBreakdown[]
```

### 3. Исправлена обработка CUSTOM дат

Теперь даты явно устанавливаются в локальную временную зону:

```typescript
if (dto.dateRangeType === DateRangeType.CUSTOM) {
  // Парсим дату и устанавливаем время на 00:00:00 в локальной временной зоне
  startDate = new Date(dto.startDate!);
  startDate.setHours(0, 0, 0, 0); // ← Явно ставим 00:00:00 по МСК
  
  // Для endDate устанавливаем 23:59:59.999
  endDate = new Date(dto.endDate!);
  endDate.setHours(23, 59, 59, 999); // ← Явно ставим конец дня
}
```

## Проверка через SQL

Для проверки данных напрямую из базы создан файл `debug-machine-uptime.sql` с запросами:

### Основной запрос для проверки всех станков:

```sql
-- Запрос #8 из debug-machine-uptime.sql
-- Показывает разбивку времени по статусам для каждого станка за сегодня
```

Этот запрос:
1. Определяет период (сегодня с 00:00 до NOW())
2. Для каждого станка находит последний статус ПЕРЕД началом периода
3. Собирает все изменения статуса В ТЕЧЕНИЕ периода
4. Рассчитывает длительность каждого статуса
5. Выводит часы и проценты для каждого статуса

## Как использовать

1. **Запустить SQL для проверки данных:**
   - Откройте `debug-machine-uptime.sql`
   - Выполните запрос #8 для проверки всех станков
   - Или запрос #7 для проверки одного станка (замените machine_id = 1 на нужный)

2. **Тестирование API:**
   ```bash
   # Запрос за сегодня
   GET /api/statistics/machine-uptime?dateRangeType=DAY
   
   # Запрос за неделю
   GET /api/statistics/machine-uptime?dateRangeType=WEEK
   
   # Запрос с фильтром по этапу
   GET /api/statistics/machine-uptime?dateRangeType=DAY&stageId=1
   ```

## Что изменилось в коде

### Файл: `machine-uptime.service.ts`

1. **getMachineUptimeStats()** - добавлен запрос для получения statusBeforePeriod
2. **calculateStatusBreakdown()** - параметр `currentStatus` переименован в `initialStatus` и используется корректно
3. **calculateDateRange()** - исправлена обработка CUSTOM дат с явной установкой времени в локальной зоне

## Тестовые сценарии

### Сценарий 1: Станок без изменений статуса
- Начальный статус: `ACTIVE`
- Изменения в период: нет
- **Результат**: 100% времени в статусе `ACTIVE` ✅

### Сценарий 2: Станок с одним изменением
- 00:00 - `ACTIVE`
- 10:00 - переключился в `INACTIVE`
- **Результат**: 
  - `ACTIVE`: 10 часов
  - `INACTIVE`: оставшееся время до конца периода ✅

### Сценарий 3: Станок с несколькими изменениями
- 00:00 - `ACTIVE`
- 08:00 - `MAINTENANCE`
- 12:00 - `ACTIVE`
- 18:00 - `INACTIVE`
- **Результат**: корректная разбивка по всем интервалам ✅

### Сценарий 4: CUSTOM период с 00:00
- Запрос: `startDate=2026-06-23&endDate=2026-06-24`
- **Было**: период с 03:00 до 03:00 (из-за UTC) ❌
- **Стало**: период с 00:00 до 23:59:59 по МСК ✅

## Важные моменты

1. **Временные зоны**: Все расчеты используют серверное время (UTC+3 согласно .env)
2. **Текущий момент**: Если период заходит в будущее, используется текущее время как конец периода
3. **Точность**: Время округляется до 2 знаков после запятой (сотые доли часа)
4. **Проценты**: Округляются до 2 знаков после запятой

## База данных

Для работы используются таблицы:
- `machines` - текущие статусы станков
- `machine_status_history` - история изменений статусов
- `machines_stages` - связь станков с этапами производства
